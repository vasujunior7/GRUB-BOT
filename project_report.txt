----------------------------------------------------------------
1. PROJECT SUMMARY
----------------------------------------------------------------
Grubbot is an autonomous fine-tuning pipeline designed to make
small local LLMs (3B–8B parameters) reliable at custom tool use.
The user defines their tools in a YAML file and a target accuracy
in a goal file. The system generates synthetic training data via
a cloud LLM (Gemini/Groq), fine-tunes a LoRA adapter using
Unsloth+TRL, evaluates against a held-out set, clusters failure
patterns using sentence-transformers + HDBSCAN, generates targeted
patch data for each failure cluster, and loops back to fine-tuning
until the accuracy target is hit or max iterations are exhausted.

Core claim: not a one-shot fine-tuner — it's a closed-loop,
failure-aware, self-correcting training system.

4. TECHNICAL DEPTH
----------------------------------------------------------------

PRINCIPLED CHOICES:
  ✓ HDBSCAN over K-Means: doesn't require predeclaring cluster
    count, handles sparse failure distributions naturally.
  ✓ Augment-and-retrain vs. replace-and-retrain: correctly
    addresses catastrophic forgetting.
  ✓ LoRA over full fine-tuning: right call at 3B–8B scale.
  ✓ LiteLLM as provider abstraction: pragmatic, one config change
    to switch providers.

SHALLOW OR UNADDRESSED:
  ✗ Evaluation methodology is the biggest technical weakness.
    "Exact key match" + "valid JSON parsing" are necessary but
    far from sufficient for production tool use.
    Missing:
    - Semantic correctness of parameter values
    - Conditional parameter validity (B depends on A's value)
    - Handling ambiguous queries mapping to multiple tools

  ✗ Distribution leak: eval set is synthetically generated by
    the SAME LLM used for training. The eval tests how well a
    student learned from a teacher's examples, graded by the
    same teacher's rubric. Does NOT measure real-world performance.

  ✗ No baseline comparison: no before/after measurement against
    un-fine-tuned Qwen2.5-3B on the same eval. You cannot claim
    the loop improves things without this.

5. SCALABILITY ANALYSIS
----------------------------------------------------------------

TOOL SET SIZE:
  • At 5 tools: trivial.
  • At 50 tools with complex interdependencies: synthetic data
    generation prompt becomes unwieldy, failure clustering space
    becomes much noisier. No architecture for multi-tool chaining.

TRAINING ITERATION COST:
  • Each loop = full LoRA training run.
  • Even with Unsloth: 15–30 min/iteration on consumer GPU (3B).
  • 5 iterations = potentially 2+ hours per pipeline run.
  • Teams updating tool definitions frequently: loop latency
    becomes a UX problem.

DATA ACCUMULATION:
  • Augment-and-retrain = training set grows unboundedly.
  • By iteration 5: potentially 3x original data.
  • No mechanism to prune low-value examples or weight recent
    targeted examples more heavily.

GPU REQUIREMENT:
  • Finetuning stage hard-requires CUDA GPU with ≥8GB VRAM.
  • Excludes: Mac-only developers, CI/CD pipelines, cloud CPU.
  • No mitigation path offered.

    General fine-tuning framework, supports tool-use datasets,
    widely adopted. No closed-loop iteration but far more
    production-hardened.

  • LlamaFactory
    Similar scope to Axolotl, supports function calling datasets,
    active community.

  • Unsloth notebooks/examples
    Ships worked examples for tool-use fine-tuning covering ~60%
    of what Grubbot does — without the loop.

  • Gorilla LLM / Berkeley Function Calling Leaderboard
    Research project benchmarking and improving LLM tool use.
    Not same UX but occupies same problem space.

  • Functionary (MeetKai)
    Small open model specifically fine-tuned for reliable function
    calling. Pre-tuned model vs. your own tools — but directly
    addresses same pain point.

  • OpenAI fine-tuning API with function calling
    For teams not restricted to local — one-click solution.

ADJACENT / INDIRECT:
  • DSPy (Stanford)
    Programmatic optimization of LLM pipelines. Covers "iterate
    until performance target" philosophy at a different abstraction.

  • LangSmith / Braintrust
    Eval-driven iteration platforms companies are building on.

GRUBBOT'S GENUINE DIFFERENTIATOR:
  Local-only + YAML-defined tools + closed-loop with failure
  clustering + no recurring API cost post-setup.
  Not directly replicated by any of the above.

7. REALISTIC CHALLENGES
----------------------------------------------------------------

CHALLENGE 1: Synthetic Eval Contamination (CRITICAL)
  Eval set generated by same LLM (Gemini/Groq) that generates
  training data. Measured accuracy improvement does NOT reliably
  predict real-world performance. A "96% accurate" Grubbot model
  may see 60–70% accuracy on actual user queries.
  → Most dangerous technical issue in current design.

CHALLENGE 2: HDBSCAN on Small Failure Sets
  HDBSCAN requires sufficient density to find clusters. At 10–20
  failures (realistic at 90%+ accuracy on 50-example eval set),
  clustering will frequently return everything as noise (label=-1).
  README demo shows "clustering 8 failures" — with 8 points in
  high-dimensional space, HDBSCAN likely produces degenerate
  results in many real scenarios.

CHALLENGE 3: LoRA Catastrophic Forgetting Over Iterations
  Each iteration retrains on ever-growing augmented dataset.
  LoRA adapters have limited capacity. After several iterations
  of targeted patching, adapter may overfit to those failure
  patterns and REGRESS on previously correct tool calls.
  No mechanism to detect or prevent this currently.

CHALLENGE 4: goal.md Parsing Fragility
  Parsing free-text Markdown to extract structured config
  (target accuracy, max iterations) via LLM call is non-
  deterministic and fragile. Introduces randomness into the
  pipeline's control flow. goal.yaml would be strictly better.

CHALLENGE 5: GPU Hard Blocker
  Core loop value proposition requires CUDA. This gates the
  product behind hardware that a significant fraction of target
  users (solo devs, regulated-industry IT) may not have.

8. BRUTALLY HONEST VERDICT
----------------------------------------------------------------

Grubbot is a genuine project with a real problem at its center,
a non-obvious architectural choice (failure clustering → targeted
augmentation), and a clear user story. It is NOT a GPT wrapper,
NOT a RAG chatbot, NOT a tutorial reimplementation. That puts it
in the top 20% of what gets submitted as portfolio work or
open-sourced in this space.

HOWEVER:

The core claim — that the loop produces reliably higher real-world
tool-use accuracy — is currently UNVERIFIABLE from what's in the
repo. The eval set is synthetic and generated by the same model
family used for training. The 96% accuracy figure in the README
demo measures self-consistency, not generalization. Any senior ML
engineer will spot this immediately. Any VC evaluating technical
moat will ask for a before/after benchmark on a human-labeled set.
The project doesn't have one.

The HDBSCAN clustering is the most novel part of the design and
also the part most likely to silently degrade at real operating
scales. The "autonomous" framing is somewhat oversold — the loop
runs without human intervention but does NOT reliably converge
on a genuinely better model in all cases.

These are fixable in weeks, not months. But in current state,
the headline performance claim is not credible.

9. SUGGESTED IMPROVEMENTS
----------------------------------------------------------------

IMPROVEMENT 1: Fix the Eval Contamination (PRIORITY: CRITICAL)
  What: Replace synthetic eval with human-curated holdout, OR
        use a DIFFERENT model family for eval generation vs.
        training. If you train on Gemini data, evaluate using
        Groq/Llama queries.
  Why: Makes the benchmark credible. Current loop's success
       criterion is unreliable without this.
  How: Add --eval-provider flag (separate from --provider).
       Report synthetic eval AND cross-model eval accuracy.

IMPROVEMENT 2: Add Baseline Before/After as First-Class Output
  What: Run un-fine-tuned base model on eval set BEFORE loop
        starts. Report delta explicitly.
        Example: "Qwen2.5-3B baseline: 52% → Grubbot v2: 96%"
  Why: This is the number that actually demonstrates value.
       Without it, 96% is meaningless to an evaluator.
  How: Add baseline_eval() call at pipeline start, log to
       runs/run_N.json, print in final summary.

IMPROVEMENT 3: HDBSCAN Brittleness Fallback
  What: When failure set < configurable threshold (e.g., <30),
        fall back to k=2/k=3 K-Means OR skip clustering and
        generate generic patch data. Document behavior explicitly.
  Why: Silent failure (everything labeled noise) is worse than
       a graceful fallback. Current behavior is a hidden failure
       mode.
  How: Add min_cluster_samples config param. Add fallback branch
       in cluster.py with explicit logging.

IMPROVEMENT 4: LoRA Regression Check Between Iterations
  What: After each retrain, run eval on PREVIOUS iteration's
        failures that were already fixed. Flag accuracy regression
        above configurable threshold. Optionally reduce LR.
  Why: Addresses catastrophic forgetting in iterative LoRA —
       a known and documented problem.
  How: Store per-example pass/fail history in runs/. Compare
       iteration N vs. N-1 on the previously-fixed subset.

IMPROVEMENT 5: Benchmark on BFCL (Berkeley Function Calling)
  What: Run Qwen2.5-3B before and after Grubbot on a subset of
        the Berkeley Function Calling Leaderboard eval set.
        Publish the delta.
  Why: One credible external benchmark makes senior ML engineers
       take the project seriously. Currently the only evidence
       is a synthetic self-generated demo.
  How: BFCL dataset is public. ~4 hours of compute to run.
       This single addition changes the project's reception
       entirely in technical circles.

IMPROVEMENT 6: Replace goal.md with goal.yaml
  What: Move structured config (target_accuracy, max_iterations,
        priorities) to goal.yaml. Keep goal.md as optional
        human-readable description only.
  Why: Parsing free-text Markdown via LLM is non-deterministic.
       goal.yaml is 2 minutes of work and eliminates an entire
       class of pipeline failures.
  How:
    target_accuracy: 0.95
    max_iterations: 5
    priority: never_hallucinate_parameters
